# JVM Incident Investigation: Part 0 — The Investigation Toolkit

> Часть 0 — введение в серию о расследовании инцидентов в JVM/Spring-приложениях.

Три часа ночи. Прод-сервис начал тормозить: латентность растёт, CPU упирается в потолок, а алерты сыплются один за другим. Вы открываете ноутбук — и что дальше? Сразу запускать профайлер? Открывать heap dump? Лезть в GC-логи наугад?

Эта серия — про то, как **методично** разбирать такие инциденты: от симптома к первопричине. И начнём мы не с конкретного инструмента, а с главного — с **инструментария и способа думать**. Потому что инструмент без правильного вопроса — это просто красивый график.

## О чём эта серия

Серия состоит из введения и восьми практических частей:

| Часть | Тема |
|---|---|
| Part 1 | CPU Profiling |
| Part 2 | Allocation Profiling / Allocation Churn |
| Part 3 | GC Profiling |

Каждая часть — это одна история: конкретный симптом, конкретный инструмент, конкретная первопричина. Всё воспроизводится в демо-приложении, которое поднимается одной командой в Docker. Репозиторий — <https://github.com/YuryKlimchuk/article-jvm-incident-investigation>; быстрый старт: `cd infra && docker compose up -d`, затем Grafana на `http://localhost:3001`, Prometheus на `http://localhost:9091`, приложение на `http://localhost:8080` (стек — Java 25, Spring Boot 4, G1GC).

## Единый алгоритм расследования

Во всех частях мы будем идти по одному и тому же маршруту:

```text
Incident → Symptoms → Measurements/Evidence → Hypothesis
→ Choose tool → Investigation → Root Cause → Fix → Verification
```

Запомните этот алгоритм — это скелет всего, что будет дальше. Инцидент случается, у него есть **симптомы** (что мы наблюдаем). Мы собираем **доказательства** (числа, метрики, сэмплы), строим **гипотезу**, выбираем **инструмент** под неё, проводим **расследование**, находим **первопричину**, чиним и **проверяем**, что полегчало.

Ключевой момент — порядок. Не «инструмент → симптом», а «симптом → вопрос → инструмент».

## Почему профайлер — не первый шаг

Соблазн велик: «сейчас запущу async-profiler и всё увижу». Но у этого подхода две проблемы.

Во-первых, профайлер отвечает на **конкретные** вопросы («где CPU?», «где аллокации?»). Если вы не знаете, что ищете, вы получите гору данных без ответа. Во-вторых, профайлер — не бесплатный: у async-profiler есть overhead, и в проде он может быть недоступен (нужны perf-события) или рискован. JFR для прода подходит лучше, но и его не стоит запускать вслепую.

Поэтому правило простое: **сначала симптом, потом вопрос, потом инструмент**.

## От симптома к вопросу

Симптом — это то, что вы *видите*: «CPU вырос», «куча ползёт вверх», «запросы встали». Вопрос — это то, что вы хотите *понять*: «какой код жжёт CPU?», «что удерживает объекты?», «кто держит блокировку?».

Один и тот же симптом может означать разные проблемы, и под каждую — свой вопрос и свой инструмент. Например:

- **Высокий CPU** — это может быть busy-loop в нашем коде, а может быть фоновый GC, который молотит из-за нехватки памяти. Вопросы разные, инструменты — разные.
- **Рост кучи** — это может быть утечка, а может быть легитимный рост: под нагрузкой приложению просто нужно больше живых объектов (live set).

Именно поэтому мы строим **матрицу решений**: симптом → вопрос → доказательства → инструмент → ожидаемый результат. Она в конце статьи.

## Инструментарий серии

Разобьём инструменты на три группы. Запомнить их легко: **смотрим внутрь JVM**, **анализируем артефакты**, **смотрим на приложение снаружи**.

### Группа 1. JVM / profiling

| Инструмент | На какие вопросы отвечает | На какие — НЕ отвечает |
|---|---|---|
| **JFR** (Java Flight Recorder) | Что происходило в JVM за период: CPU, аллокации, GC, блокировки, I/O | Не показывает содержимое кучи (кто на кого ссылается) |
| **async-profiler** | Где CPU и где аллокации (сэмплирование, малый overhead) | Покрывает не весь спектр событий JFR (CPU/alloc/lock, а не «всё подряд»); не анализирует кучу |
| **jcmd** | Управление JVM: снять heap dump, стартовать JFR, NMT-отчёты | Это «пульт», а не сам анализатор |
| **jstack** | Мгновенный снимок потоков: кто что делает, кто кого заблокировал | Только момент времени; не показывает историю |
| **GC-логи** | Как работает сборщик: частота, паузы, фазы, причины | Не показывают, *что* аллоцирует (для этого нужен профайлер) |
| **NMT** (Native Memory Tracking) | Куда уходит native-память: threads, metaspace, code, malloc (требует включения при старте JVM) | Не показывает объекты/ссылки внутри кучи; call sites аллокаций — только в режиме detail |

### Группа 2. Анализ артефактов

| Инструмент | На какие вопросы отвечает | На какие — НЕ отвечает |
|---|---|---|
| **JMC** (JDK Mission Control) | Анализ JFR-записей: горячие методы, события, таймлайны | Для heap dump основной инструмент — MAT (в JMC есть JOverflow, но пути до GC root ищут в MAT) |
| **MAT** (Eclipse Memory Analyzer) | Что удерживает объекты в heap dump, пути до GC root | Не показывает поведение во времени |

### Группа 3. Application / инфраструктура

| Инструмент | На какие вопросы отвечает | На какие — НЕ отвечает |
|---|---|---|
| **Micrometer** | Метрики приложения изнутри: JVM, HTTP, пулы + системные (CPU) | Не видит внешнюю инфраструктуру (другие сервисы, сеть); не отдаёт RSS процесса; не профилирует код |
| **Prometheus** | Хранение и запросы метрик (PromQL), тренды | Сам по себе не профилирует код |
| **Grafana** | Визуализация метрик, дашборды | Не собирает данные — только рисует |
| **HikariCP metrics** | Состояние пула соединений: active/pending/timeouts | Не показывают сами SQL-запросы |
| **PostgreSQL statistics** | Что происходит в БД: активные соединения, медленные запросы | Не показывают код приложения |
| **OS / контейнер** (top, pidstat, cAdvisor) | CPU/RSS/I/O/fd процесса и контейнера — где подтверждается сам симптом | Не показывают, что происходит внутри JVM |

Ключевая идея этой таблицы: **ни один инструмент не покрывает всё**. У каждого есть зона, где он силён, и зона, где он слеп. Расследование — это переходы между ними.

## Как инструменты дополняют друг друга

Типичная цепочка выглядит так:

```text
метрики (Grafana) → локализовали проблему
→ профайлер (async-profiler / JFR) → нашли горячую точку
→ heap dump / thread dump → подтвердили первопричину
```

Пример: куча растёт. Сначала смотрим метрики — heap used ползёт вверх. Формулируем вопрос: «утечка или рост живого набора?». Снимаем heap dump — и в MAT видим, что коллекция удерживает миллион объектов. Первопричина найдена.

Другой пример: запросы к БД тормозят. Метрики показывают, что HikariCP пул исчерпан (active = max, pending растёт). Теперь главный вопрос — почему соединения не возвращаются. Основных сценариев несколько: медленный SQL (соединение легитимно занято), зависшая транзакция (`idle in transaction`), утечка (забыли закрыть) или просто маленький пул под текущую нагрузку. Идём в `pg_stat_activity`: `active` без `wait_event = ClientRead/ClientWrite` — реально медленный SQL; `idle in transaction` — открыта зависшая транзакция (например, `@Transactional` вокруг внешнего вызова); а «забыли закрыть» без транзакции выглядит как обычный `idle` — его ловят рассинхроном: HikariCP `active` высокий, а на стороне БД всё `idle`.

## Парные сравнения: когда что выбирать

### JFR vs async-profiler

- **JFR** — это «бортовой самописец» JVM: включил, он записывает включённые события (CPU, аллокации, GC, блокировки, I/O) с низким overhead. Удобен, когда проблема **не воспроизводится на ровном месте** и нужна запись «вокруг инцидента» — но для этого continuous JFR с кольцевым буфером должен быть включён заранее: `JFR.start` задним числом ничего не запишет.
- **async-profiler** — точечный инструмент: сэмплирует CPU или аллокации, даёт flame graph. Лучше, когда нужен **точный профиль конкретного аспекта** (CPU/аллокации).

Правило: не знаешь, что искать — JFR. Знаешь, что нужен CPU/аллокации — async-profiler.

### JFR vs thread dump

- **thread dump (jstack / `jcmd Thread.print`)** — мгновенный снимок: «что происходит прямо сейчас». Обычно дёшево, но это safepoint-операция; на большом числе потоков снимайте 3–5 дампов подряд.
- **JFR** — запись во времени: видно, как менялись состояния потоков, кто и когда брал блокировку.

Правило: зависло «прямо сейчас» — thread dump. Проблема «плавает» во времени — JFR.

### Heap dump vs JFR

- **heap dump** — про **содержимое** кучи: кто на кого ссылается. Отвечает на «почему объект жив».
- **JFR** — про **поведение** во времени: кто аллоцирует, как часто GC.

Снятие heap dump на большом хипе — не бесплатная операция: возможна GC-пауза и крупный файл. При OOM полезен `-XX:+HeapDumpOnOutOfMemoryError`.

Правило: объекты не собираются / куча растёт — heap dump. Поведение во времени (аллокации, GC, CPU) — JFR.

### Когда нужен NMT

NMT нужен, когда **профилирование кучи недостаточно**: RSS процесса растёт, а Java-куча в норме. Значит, память уходит в native. Важная оговорка: NMT включается только при старте JVM (`-XX:NativeMemoryTracking=summary|detail`) — без этого флага `jcmd VM.native_memory` в момент инцидента вернёт «not enabled». И NMT в режиме `summary` показывает **категорию и объём**, а в режиме `detail` — ещё и call sites аллокаций (ценой заметного overhead). Если трекинг не был включён, альтернативы — `pmap`, `/proc/<pid>/smaps`, jemalloc или async-profiler.

## Почему метрики важны до JVM-уровня

Прежде чем лезть в профайлер, посмотрите на **application-метрики**. Они отвечают на вопрос «где именно болит»: это наш код, БД, внешний сервис или пул соединений?

- HTTP-метрики (Micrometer) покажут, какие эндпоинты тормозят.
- HikariCP покажет, исчерпан ли пул.
- PostgreSQL statistics покажет, тупит ли сама БД.

Только локализовав проблему на уровне приложения, есть смысл опускаться на JVM-уровень. Иначе можно долго профилировать CPU, пока настоящая проблема — утечка соединений.

## Матрица принятия решений

Главная таблица этой статьи. Слева — симптом, справа — что с ним делать.

| Симптом | Вопрос | Доказательства | Инструмент | Ожидаемый результат |
|---|---|---|---|---|
| High CPU | Какой код жжёт CPU? | Сэмплы потоков во времени | async-profiler (cpu), JFR | Горячий метод + дерево вызовов |
| High allocation rate | Где аллоцируются объекты? | Сэмплы аллокаций | async-profiler (alloc), JFR | Горячие точки аллокаций |
| Frequent GC | Почему GC частый? | GC-логи + темп аллокаций | GC-логи, JFR | Темп аллокаций vs размер кучи (что провоцирует GC) |
| Long GC pauses | Какая фаза паузит? | Тайминги фаз GC | GC-логи, JFR | Длительность пауз по фазам |
| Growing heap | Утечка или легитимный рост? | Тренд кучи + оценка live set (куча после сборки) | GC-логи + heap dump | retained vs live set |
| Suspected memory leak | Что удерживает объекты? | Heap dump | MAT (leak suspects) | Путь до GC root |
| High RSS, нормальная куча | Куда уходит native-память? | Отчёт NMT | jcmd VM.native_memory (нужен -XX:NativeMemoryTracking при старте) | Категория (threads/metaspace/malloc) |
| Too many threads | Что за потоки и почему их много? | Список потоков | jstack, JFR | Имя/стек/количество по состояниям |
| Blocked threads | Кто держит блокировку? | Thread dump | jstack | Владелец блокировки |
| Deadlock | Какой цикл блокировок? | Thread dump | jstack (found deadlock) | Цикл A→B→C→A |
| Slow database requests | SQL, пул или сеть? | Метрики HikariCP + PostgreSQL | HikariCP, pg_stat_activity / pg_stat_statements (extension) | Медленный запрос vs ожидание |
| Connection pool exhaustion | Утечка, медленный SQL или малый пул? | Метрики HikariCP | HikariCP metrics | Утечка vs медленный SQL vs малый пул |
| Slow external HTTP calls | Латентность, throughput, таймауты? | Метрики HTTP-клиента | Micrometer (тайминги), JFR (socket I/O) | p50/p99 (Micrometer), сокетный I/O (JFR) |
