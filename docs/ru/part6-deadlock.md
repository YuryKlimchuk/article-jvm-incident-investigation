# JVM Incident Investigation: Part 6 — Threads, Locks & Deadlocks

Приложение «зависло»: часть запросов просто не отвечает. CPU почти нулевой, куча в норме, памяти хватает — а сервис стоит. Такой симптом не лечится профайлером CPU и не ищется в heap dump. Проблема — в потоках, которые застряли на блокировках.

У нас есть демо-приложение с «красной кнопкой»: ручка, которая запускает два потока, берущих два лока в противоположном порядке. Пройдём весь путь от симптома до первопричины — с реальным thread dump.

## Симптом: зависло, но ресурсы в норме

Включаем проблему:

```bash
scripts/incidents.sh start deadlock
```

Ответ:

```json
{ "type": "deadlock", "status": "active", "description": "проблема активирована" }
```

Внешне ничего не «горит»: `process_cpu_usage` остаётся ~0.0008 — это доля CPU всей машины, то есть практически ноль (потоки не крутятся, они ждут), куча `jvm_memory_used_bytes{area="heap",id="G1 Old Gen"}` — ~20 МБ. Но вот метрика потоков по состояниям меняется: `jvm_threads_states_threads{state="blocked"}` вырастает с 0 до 2.

Это и есть сигнатура проблемы с блокировками: **ресурсы (CPU/память) в норме, а потоки застревают в BLOCKED**. Приложение не работает не потому, что ему не хватает ресурсов, а потому, что потоки не могут друг друга дождаться.

## Дашборд: Part 6 — Threads, Locks & Deadlocks

Карта наблюдения — три панели:

| Панель | Метрика | Что показывает | Что ждём при инциденте |
|---|---|---|---|
| Live threads | `jvm_threads_live_threads` | число живых потоков | почти не меняется (deadlock не плодит потоки) |
| Peak threads | `jvm_threads_peak_threads` | пик с момента старта | почти не меняется |
| Threads by state | `jvm_threads_states_threads` | потоки по состояниям | растёт `state="blocked"` |

Главная панель — третья. Deadlock не создаёт новые потоки и не грузит CPU — он переводит существующие потоки в состояние `BLOCKED` (ждут монитор). Поэтому смотреть надо именно на распределение потоков по состояниям, а не на их общее число.

## Вопрос

Симптом — «приложение зависло, ресурсы в норме». По методике из Part 0 формулируем вопрос: **«где именно зависли потоки и кто кого ждёт?»**.

Прежние инструменты не подходят. Профайлер CPU покажет почти ничего (потоки не исполняются — они ждут). Heap dump — память в порядке. Нужен инструмент, который показывает *состояние потоков и блокировки* — thread dump.

## Диагностика: thread dump

Thread dump — это мгновенный снимок всех потоков: кто в каком состоянии, что исполняет, какой монитор держит, какой ждёт. Снимаем:

```bash
docker exec app jcmd 1 Thread.print
```

В выводе сразу видим блок, ради которого всё и затевалось:

```text
Found one Java-level deadlock:
=============================
"deadlock-a-then-b":
  waiting to lock monitor 0x00007aa200003bd0 (object 0x00000006115c52c0, a java.lang.Object),
  which is held by "deadlock-b-then-a"

"deadlock-b-then-a":
  waiting to lock monitor 0x00007aa198001070 (object 0x00000006115c52b0, a java.lang.Object),
  which is held by "deadlock-a-then-b"

Java stack information for the threads listed above:
===================================================
"deadlock-a-then-b":
	at com.hydroyura.article.jvmincidents.incident.deadlock.DeadlockIncident.lambda$doStart$0(DeadlockIncident.java:29)
	- waiting to lock <0x00000006115c52c0> (a java.lang.Object)
	- locked <0x00000006115c52b0> (a java.lang.Object)
"deadlock-b-then-a":
	at com.hydroyura.article.jvmincidents.incident.deadlock.DeadlockIncident.lambda$doStart$1(DeadlockIncident.java:37)
	- waiting to lock <0x00000006115c52b0> (a java.lang.Object)
	- locked <0x00000006115c52c0> (a java.lang.Object)
```

JVM сама диагностировала deadlock и вывела цикл: поток `deadlock-a-then-b` держит объект A и ждёт B, а `deadlock-b-then-a` держит B и ждёт A. Каждый ждёт то, что держит другой. Круг замкнулся.

В дампе это подтверждается и косвенно: оба потока в состоянии `waiting for monitor entry` — это текстовое обозначение в thread dump того самого состояния `BLOCKED`, которое мы видели в метриках, с `cpu≈0` (они не работают, они стоят). Это отличает deadlock от busy-loop из Part 1, где потоки были `RUNNABLE` с `cpu≈100%`.

## Первопричина

Смотрим код инцидента:

```java
Thread t1 = new Thread(() -> {
    synchronized (lockA) {
        sleep(50);
        synchronized (lockB) {
            // никогда не достигнется
        }
    }
}, "deadlock-a-then-b");

Thread t2 = new Thread(() -> {
    synchronized (lockB) {
        sleep(50);
        synchronized (lockA) {
            // никогда не достигнется
        }
    }
}, "deadlock-b-then-a");
```

Первопричина — **неконсистентный порядок захвата локов**. Один поток берёт `lockA`, потом `lockB`; второй — `lockB`, потом `lockA`. Если первый успел взять `lockA`, а второй — `lockB`, дальше оба застревают: первому нужен `lockB` (занят вторым), второму — `lockA` (занят первым).

`sleep(50)` в коде — не причина, а «усилитель»: он увеличивает окно, в котором потоки успевают пересечься в середине захвата. Без `sleep` deadlock тоже возможен, просто менее детерминирован. Причина — именно порядок локов.

В проде это выглядит как угодно: два сервиса берут общие ресурсы в разном порядке, вложенные `synchronized`-блоки, транзакции с разным порядком захвата строк в БД. Суть одна — **цикл ожидания, где каждый держит то, что нужно другому**. Оговорка: автоматическая детекция «Found one Java-level deadlock» хорошо работает для `synchronized`-мониторов. Для `java.util.concurrent` локов (`ReentrantLock` и других ownable synchronizers) JVM тоже умеет находить циклы — но для этого нужен флаг `-l` (`jcmd 1 Thread.print -l`), который показывает владельцев таких локов; без него дамп покажет только состояния `WAITING`, и цикл придётся восстанавливать вручную.

## Фикс и проверка

Правильный фикс — **единый порядок захвата локов**: всегда `lockA` → `lockB`, никогда наоборот. Демо-ручка `fix` показывает это на свежих локах:

```bash
scripts/incidents.sh fix deadlock
```

`doFix()` запускает два потока `fixed-lock-order-1`/`fixed-lock-order-2`, которые берут `a`, затем `b` — и нормально завершаются. Это демонстрация принципа.

Но вот важная и честная оговорка: **уже возникший deadlock так не снять**. Потоки `deadlock-a-then-b`/`deadlock-b-then-a` остаются `BLOCKED` — `fix`/`stop` не могут их прервать, потому что они застряли на мониторе. Даже после `stop deadlock` (статус вернулся в `idle`) метрика `state="blocked"` по-прежнему показывает 2. Единственный способ полного сброса реального deadlock — перезапуск процесса.

```bash
scripts/incidents.sh stop deadlock          # статус idle, но потоки всё ещё BLOCKED
docker compose -f infra/docker-compose.yml restart app   # единственный полный сброс
```

В реальном коде фикс — это код-ревью на порядок локов: зафиксировать глобальный порядок, уменьшить число одновременно удерживаемых локов, использовать `tryLock` с таймаутом там, где порядок нельзя гарантировать. Но зависший инцидент на проде всё равно часто заканчивается рестартом — это нормальная часть восстановления.

## Родственный симптом: too many threads

Рядом в демо есть инцидент `threads` — другой, но похожий по «потоковому» профилю. `start threads` спавнит 500 потоков, которые вечно спят:

```text
jvm_threads_live_threads                         26  → 526
jvm_threads_states_threads{state="timed-waiting"}  4 → 504
```

Здесь проблема не в блокировках, а в **неограниченном создании потоков** (нет пула, каждый запрос — новый поток, который не завершается). Признак — линейный рост `jvm_threads_live_threads` и `timed-waiting`, а в thread dump **нет** блока deadlock. Симптомы разные, инструмент один и тот же (thread dump), но интерпретация разная: deadlock = цикл в блокировках, thread exhaustion = слишком много спящих потоков.

## Что мы сделали

Полный алгоритм из Part 0 на конкретном инциденте:

```
симптом (зависло, CPU/память в норме)
→ вопрос (где зависли потоки и кто кого ждёт?)
→ thread dump (jcmd Thread.print)
→ первопричина (неконсистентный порядок локов A→B vs B→A)
→ fix + проверка (единый порядок; реальный deadlock требует рестарта)
```

Сравнение по «растущему ресурсу»:

| Часть | Что растёт / симптом |
|---|---|
| Part 1 CPU | CPU |
| Part 2 allocation churn | темп аллокаций |
| Part 3 humongous | Old Gen / GC-паузы |
| Part 4 memory leak | куча (не возвращается) |
| Part 5 native | RSS (куча в норме) |
| **Part 6 deadlock** | **число blocked-потоков (ресурсы в норме)** |

Ключевой урок этой части: **когда ресурсы в норме, а сервис «стоит» — смотрите на потоки и блокировки**. Thread dump — дешёвый и прямой инструмент для этого, и JVM сама подсвечивает deadlock.
