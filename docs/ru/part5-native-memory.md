# JVM Incident Investigation: Part 5 — Native Memory

RSS контейнера растёт, а Java-куча стоит на месте. Это тревожный звонок для любого, кто привык смотреть только на heap: в Part 4 у нас росла именно куча (утечка объектов), а здесь куча в норме, но память всё равно утекает — в native.

У нас есть демо-приложение с «красной кнопкой»: ручка, которая выделяет прямые (direct) буферы и никогда их не освобождает. Пройдём весь путь от симптома до первопричины — с реальными командами и реальными метриками.

## Симптом: RSS растёт, куча молчит

Включаем проблему:

```bash
scripts/incidents.sh start native-memory
```

Ответ:

```json
{ "type": "native-memory", "status": "active", "description": "проблема активирована" }
```

На свежем рестарте `app` (стек демо — Java 25, G1GC) снимаем baseline и следим за тремя метриками. Вот что происходит с прямыми буферами `jvm_buffer_memory_used_bytes{id="direct"}`:

```text
baseline       10 КБ
+15 секунд    157 МБ
+30 секунд    313 МБ
+60 секунд    625 МБ
```

Прямые буферы растут линейно, ~10 МБ/с. При этом Java-куча `jvm_memory_used_bytes{area="heap"}` остаётся на месте — около 40 МБ во время всего инцидента. А вот RSS контейнера (`container_memory_rss` из cAdvisor) растёт: с ~267 МБ в покое до ~903 МБ.

Это и есть сигнатура native-утечки: **куча в норме, а память процесса растёт**. Объекты в куче — лишь крошечные обёртки `ByteBuffer`, а сама память (по 1 МБ на буфер) выделяется вне кучи.

## Дашборд: Part 5 — Native Memory

Карта наблюдения — три панели:

| Панель | Метрика | Что показывает | Что ждём при инциденте |
|---|---|---|---|
| Container RSS (app) | `container_memory_rss{...service="app"}` | физическая память контейнера | растёт — native-память утекает |
| Heap used | `jvm_memory_used_bytes{area="heap"}` | занятая Java-куча | почти не меняется — куча ни при чём |
| Direct buffers | `jvm_buffer_memory_used_bytes{id="direct"}` | объём прямых буферов | растёт — вот куда уходит память |

Ключевое сочетание — первая и вторая панели вместе. Если RSS растёт, а heap стоит на месте, то смотреть в heap dump бессмысленно: утечка не в объектах кучи. Третья панель сразу подсказывает виновника — прямые буферы.

## Вопрос

Симптом — «память уходит, куча в норме». По методике из Part 0 формулируем вопрос: **«куда именно уходит native-память?»**.

Здесь инструмент Part 4 (heap dump) не покажет главное: сами native-буферы лежат вне кучи, и их мегабайты в дамп не попадают. Но обёртки `ByteBuffer` и удерживающая их статическая коллекция в куче видны — если нужно найти *владельца* утечки, heap dump пригодится. Однако сначала локализовать, *куда* уходит память, должен инструмент, который смотрит на native-память JVM, а не на кучу.

## Диагностика: NMT

Инструмент для этого — Native Memory Tracking (NMT). Он раскладывает всю native-память JVM по категориям: Java Heap, Class (метаданные), Thread (стеки), Code (JIT), GC и другие. Ключевая деталь: **NMT включается только при старте JVM** флагом `-XX:NativeMemoryTracking=summary`. Если флага нет — `jcmd VM.native_memory` в момент инцидента вернёт «not enabled», и задним числом включить его нельзя.

В нашем демо флаг уже стоит в Dockerfile:

```bash
docker exec app jcmd 1 VM.flags | grep NativeMemoryTracking
# -XX:NativeMemoryTracking=summary
```

Дальше снимаем baseline и сравниваем после роста:

```bash
docker exec app jcmd 1 VM.native_memory baseline
# ... инцидент активен, память выросла ...
docker exec app jcmd 1 VM.native_memory summary.diff
```

В diff смотрим, какая категория выросла:

```text
-                     Other (reserved=814214KB +814150KB, committed=814214KB +814150KB)
                            (malloc=812166KB +812102KB #816 +807)
-                 Java Heap (reserved=8138752KB, committed=294912KB +221184KB)
```

Категория **`Other`** выросла на ~814 МБ — это и есть наши прямые буферы (снято чуть позже, чем метрика на +60с, поэтому больше, чем 625 МБ; точное имя категории direct-буферов может быть `Other` или `Internal` в зависимости от версии JDK). Прямые `ByteBuffer` выделяются вне кучи (нативно, через `malloc`), поэтому NMT относит их к `Other`, а не к Java Heap. Категория `Java Heap` по committed выросла скромно (+216 МБ — JVM выделила под кучу физическую память, это committed, в отличие от reserved адресного пространства), но её «used» (живые объекты) остался на ~40 МБ — вся утечка сидит в `Other`, а не в куче.

Это и есть ответ на вопрос: память уходит в **`Other` → malloc**, то есть в прямые буферы, которые никто не освобождает.

## Диагностика без NMT (альтернативы)

Если NMT не был включён заранее, есть запасные варианты — грубее, но они работают.

Смотрим на уровне процесса через `pmap`:

```bash
docker exec app pmap -x 1
```

```text
Address           Kbytes     RSS   Dirty Mode  Mapping
0000000067000000       4       4       4 -----   [ anon ]
...
```

`pmap` показывает регионы памяти процесса. При native-утечке будет расти какой-то анонимный (`[ anon ]`) регион, сопоставимый по размеру с приростом RSS. Минус в том, что `pmap` не говорит, *какой код* эту память выделил — только «вот растёт анонимный кусок».

Ещё вариант — `/proc/<pid>/smaps` с той же идеей, но с детализацией по регионам. Оба инструмента подтверждают симптом на уровне ОС, но не заменяют NMT: они не показывают категорию JVM. Поэтому в проде стоит заранее включать `-XX:NativeMemoryTracking=summary` — это дёшево и спасает от слепой диагностики.

## Первопричина

Смотрим код инцидента:

```java
private static final List<ByteBuffer> BUFFERS = new ArrayList<>();

@Override
protected void doStart() {
    running.set(true);
    thread = new Thread(() -> {
        while (running.get()) {
            BUFFERS.add(ByteBuffer.allocateDirect(1024 * 1024)); // 1 MB native
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }, "native-allocator");
    thread.setDaemon(true);
    thread.start();
}
```

Поток `native-allocator` каждые 100 мс кладёт в статическую коллекцию новый прямой буфер на 1 МБ — и не удаляет. `allocateDirect` выделяет память вне кучи (через `Unsafe.allocateMemory`), а в куче остаётся лишь маленький объект `ByteBuffer` с Cleaner. Отсюда и расхождение: heap стабилен, а RSS растёт.

Почему heap dump не покажет объём утечки: сами native-буферы лежат за пределами кучи, поэтому в дампе мы увидим только тысячи крошечных `ByteBuffer`-обёрток (суммарно мегабайты) — а вот эта картина, кстати, и есть улика для поиска *владельца*: удерживающая статическая коллекция видна. Но объём утечки heap dump не покажет — для него нужен NMT.

В проде этот паттерн выглядит знакомо: прямые буферы под сетевой I/O, off-heap кэши, JNI-библиотеки, `Unsafe`-аллокации. Суть одна — **память выделяется вне кучи и не освобождается**. Кстати про лимиты: прямые буферы ограничены `-XX:MaxDirectMemorySize` (по умолчанию равен `-Xmx`). Пока лимит не достигнут, JVM не падает — просто растёт RSS; когда исчерпан, получите `OutOfMemoryError: Direct buffer memory`.

## Фикс и проверка

Выключаем проблему:

```bash
scripts/incidents.sh fix native-memory
scripts/incidents.sh stop native-memory
```

`fix`/`stop` вызывают `release()`: останавливают поток, чистят коллекцию `BUFFERS.clear()` и делают `System.gc()`. Зачем принудительный GC при native-утечке? Прямой буфер — это крошечная обёртка в куче, к которой привязан `Cleaner`; native-память возвращается, только когда GC соберёт эту обёртку. А раз куча почти пуста (~40 МБ), давления на неё нет, и GC сам может не запуститься — поэтому вызываем его явно. (Оговорка для прода: `System.gc()` может быть отключён `-XX:+DisableExplicitGC`, тогда Cleaner сработает только при естественной сборке.) Проверяем:

```text
jvm_buffer_memory_used_bytes{id="direct"}  10 КБ
```

Прямые буферы вернулись с 625 МБ к baseline 10 КБ. RSS тоже опускается к ~267 МБ (с задержкой — ОС не всегда сразу отдаёт освобождённую память). Проверка пройдена: утечка была именно в native-буферах.

В реальном коде «фикс» — это устранить источник: закрывать/освобождать прямые буферы явно, использовать пул буферов, ограничить размер off-heap кэша. Демо-ручка показывает принцип: убрать ссылки → дать Cleaner/GC шанс → память вернулась.

## Что мы сделали

Полный алгоритм из Part 0 на конкретном инциденте:

```
симптом (RSS растёт, heap стабилен)
→ вопрос (куда уходит native-память?)
→ NMT (VM.native_memory baseline → summary.diff)
→ первопричина (direct ByteBuffers в категории Other, без освобождения)
→ fix + проверка (clear + System.gc → память вернулась)
```

Сравнение двух «утечек» серии:

| | Part 4 heap leak | Part 5 native leak |
|---|---|---|
| Что растёт | Java-куча | RSS / native-память |
| Куча | растёт | **стабильна** |
| Инструмент | heap dump + MAT | NMT / pmap |
| Heap dump | находит причину | не покажет объём (найдёт владельца через обёртки) |

Ключевой урок этой части: **если RSS растёт, а heap в норме — забудьте про heap dump, включайте NMT**. Разные виды памяти диагностируются разными инструментами, и смотреть надо туда, где на самом деле растёт.
