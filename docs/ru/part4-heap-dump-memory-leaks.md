# JVM Incident Investigation: Part 4 — Heap Dump & Memory Leaks

Куча в Grafana растёт и — вот что отличает этот симптом от предыдущих — **не возвращается к baseline**. В Part 2 куча была стабильна при бешеном темпе аллокаций, в Part 3 Old Gen рос только во время инцидента и падал после `stop`. А здесь, даже после принудительного Full GC, занятая куча остаётся на достигнутом уровне. Это классический признак memory leak.

У нас есть демо-приложение с «красной кнопкой»: ручка, которая включает поток, складывающий объекты в статическую коллекцию без очистки. Пройдём весь путь от симптома до первопричины — с реальными командами, реальными метриками и реальными дампами кучи.

## Симптом: куча растёт и не возвращается

Включаем проблему:

```bash
scripts/incidents.sh start memory-leak
```

Ответ:

```json
{ "type": "memory-leak", "status": "active", "description": "проблема активирована" }
```

До запуска, на свежем рестарте `app` (стек демо — Java 25, G1GC), занятая куча в Old Gen была ~20 МБ, а `jvm_gc_live_data_size_bytes` (живой набор после сборки) — ещё 0: эта метрика обновляется только после полной сборки, которой в покое не было. Запускаем и следим за `jvm_memory_used_bytes{area="heap",id="G1 Old Gen"}`:

```text
baseline     ~20 МБ
+15 секунд    ~145 МБ
+30 секунд    ~408 МБ
+60 секунд    ~858 МБ
```

Рост линейный, ~10 МБ/с. Пока это ничем не отличается от Part 3 — мало ли, куча заполнилась. Ключевой тест впереди: **принудительный Full GC**.

```bash
docker exec app jcmd 1 GC.run
```

После Full GC смотрим кучу снова:

```text
jvm_memory_used_bytes{area="heap",id="G1 Old Gen"}  704 МБ
jvm_gc_live_data_size_bytes                         704 МБ
```

Сборщик отработал, но куча **не вернулась** к ~20 МБ — она осталась на ~704 МБ. Это и есть сигнатура утечки: объекты не собираются, потому что на них кто-то держит ссылку. В Part 2/3 после остановки нагрузки куча падала к baseline, а здесь — нет.

## Дашборд: Part 4 — Heap Dump & Memory Leaks

Карта наблюдения — три панели:

| Панель | Метрика | Что показывает | Что ждём при инциденте |
|---|---|---|---|
| Heap used | `jvm_memory_used_bytes{area="heap"}` | занятая куча | растёт линейно, не падает |
| Heap committed | `jvm_memory_committed_bytes{area="heap"}` | зарезервированная JVM куча | растёт вслед за used, не отдаёт память |
| Live data size (after GC) | `jvm_gc_live_data_size_bytes` | живой набор после сборки | растёт — это «неубиваемый» остаток |

Третья панель — самая информативная для утечки. `jvm_gc_live_data_size_bytes` обновляется после полной сборки и показывает, сколько памяти занято **живыми** объектами, которые GC не смог вычистить. Если эта метрика растёт от сборки к сборке — перед нами не «мусор, который ещё не собрали», а объекты, которые не могут быть собраны.

## Вопрос

Симптом — «куча растёт». По методике из Part 0 формулируем вопрос: **«утечка или легитимный рост живого набора?»**.

Это принципиальное различие, и от него зависит инструмент:

- **Легитимный рост live set** — приложение под нагрузкой держит больше живых объектов (кэш, сессии, рабочий набор). После Full GC и снятия нагрузки такой набор стабилизируется и не растёт бесконечно.
- **Memory leak** — объекты перестают быть нужны, но ссылка на них остаётся, поэтому они копятся без ограничения. После Full GC они никуда не деваются, а retained set продолжает расти от снимка к снимку.

Наблюдаемый критерий различения — **поведение после Full GC и во времени**, а не абсолютное значение кучи в один момент. Один снимок ничего не говорит; нужно два снимка с интервалом.

## Диагностика: heap dump

Метрики подтвердили симптом, теперь нужно доказать его на уровне объектов. Снимаем heap dump во время активного инцидента:

```bash
docker exec app jcmd 1 GC.heap_dump /artifacts/leak-active.hprof
# Heap dump file created [722838832 bytes in 0.553 secs]
```

Файл ~723 МБ. Через полторы минуты снимаем второй снимок, не останавливая поток:

```bash
docker exec app jcmd 1 GC.heap_dump /artifacts/leak-active-2.hprof
# Heap dump file created [1384525722 bytes in 0.879 secs]
```

Второй файл уже ~1.38 ГБ. Сам по себе рост размера dump — лишь косвенный признак, что куча выросла (файл включает служебные структуры, а не только живые объекты). Прямое доказательство роста живого набора — в `class_histogram` и поведении после Full GC ниже.

Зачем ручной `jcmd GC.heap_dump`, а не `-XX:+HeapDumpOnOutOfMemoryError`? Второй флаг в Dockerfile уже есть, но это защитная сетка на случай реального OOM. Для воспроизводимой статьи ждать OOM — дорого и нестабильно (контейнер упадёт, придётся восстанавливать). Ручной снимок даёт тот же hprof-файл в любой момент, без падения.

Оговорка для прода: `GC.heap_dump` — это stop-the-world операция, на время записи файла приложение замирает. На демо это незаметно, на проде с большим хипом пауза может быть ощутимой — снимайте дамп осознанно.

## Диагностика: MAT

Снимок есть, дальше — анализ. Канонический инструмент для heap dump — Eclipse MAT. Он даёт три отчёта, которые последовательно сужают поиск.

Пока dump анализируется, заглянем в живую кучу через встроенную в JVM команду — она даёт ту же «топ-класс» картину, что и Histogram в MAT. (Сам анализ гигабайтного hprof в MAT требует индексации и памяти — для файла на 1.38 ГБ MAT понадобится в 2–3 раза больше `-Xmx`, чем размер снимка.)

```bash
docker exec app jcmd 1 GC.class_histogram
```

```text
 num     #instances         #bytes  class name
   1:         85386      318949384  [B
   2:         79305        1903320  java.lang.String
   3:         12650        1601200  java.lang.Class
```

Класс `byte[]` (`[B`) доминирует с огромным отрывом: ~85 000 инстансов на ~304 МБ, тогда как всё остальное — единицы мегабайт. Это уже прямая улика: утечка — массив `byte[]`. Размер HPROF-файлов (723 МБ → 1.38 ГБ) — лишь косвенный признак роста кучи (файл включает служебные структуры), а не retained set; сам живой набор виден в `class_histogram` (~304 МБ на момент снятия) и продолжает расти, пока работает поток.

Дальше канонический путь в MAT уточняет *удерживающую ссылку* — и для нашего кода он детерминирован:

1. **Leak Suspects** — автоматический отчёт указывает на подозрительную коллекцию: здесь это `ArrayList`, удерживающий массив `byte[]`.
2. **Dominator Tree** — показывает retained size: сколько освободится при сборке объекта. Для `ArrayList` из статического поля это те самые ~300+ МБ.
3. **Path to GC Root** — путь от объекта до корня. Цепочка ведёт в статическое поле `MemoryLeakIncident.LEAKED` (разбираем в «Первопричине»).

Ключевой тест на различение утечки и легитимного роста — поведение после Full GC: при легитимном росте occupancy после Full GC стабилизируется, а у нас она не вернулась к baseline (осталась ~704 МБ), пока удерживающая ссылка на месте. Рост не остановился — значит, это утечка.

## Первопричина

Смотрим код инцидента:

```java
private static final List<byte[]> LEAKED = new ArrayList<>();

@Override
protected void doStart() {
    running.set(true);
    thread = new Thread(() -> {
        while (running.get()) {
            LEAKED.add(new byte[1024 * 1024]); // 1 MB удерживается
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }, "memory-leaker");
    thread.setDaemon(true);
    thread.start();
}
```

Классическая «static collection leak». Поток `memory-leaker` каждые 100 мс кладёт в статический `List<byte[]> LEAKED` новый массив на 1 МБ — и **никогда его оттуда не удаляет**. Статическое поле живёт, пока живёт класс (то есть вечно), поэтому GC не может собрать ни сами массивы, ни ссылки на них.

Именно эту цепочку показывает Path to GC Root в MAT: `byte[]` → внутренний массив `ArrayList` → сам `ArrayList` → статическое поле `MemoryLeakIncident.LEAKED` → class loader (GC root). Объекты «застряли» не потому, что на них ссылается работающий код, а потому, что их держит глобальная коллекция, которая никогда не чистится.

В проде это выглядит как угодно, но суть одна: `static`-кэш без ограничения размера, слушатель, который забыли отписать, регистр, куда добавляют, но откуда не удаляют. Каждый такой паттерн — это удерживающая ссылка, которая копит объекты.

## Фикс и проверка

Выключаем проблему:

```bash
scripts/incidents.sh fix memory-leak
scripts/incidents.sh stop memory-leak
```

`fix`/`stop` вызывают `stopAndClear()`: останавливают поток и **очищают коллекцию** `LEAKED.clear()`. После этого принудительный Full GC:

```bash
docker exec app jcmd 1 GC.run
```

```text
jvm_memory_used_bytes{area="heap",id="G1 Old Gen"}  22.5 МБ
jvm_gc_live_data_size_bytes                         22.5 МБ
```

Куча упала с ~704 МБ обратно к ~22 МБ — почти к baseline. Удерживающая ссылка исчезла, и GC наконец смог вычистить массивы. Проверка пройдена: проблема была именно в накоплении, а не в легитимном росте.

В реальном коде «фикс» — это устранить удерживающую ссылку: ограничить размер кэша (bounded cache / LRU), использовать слабые ссылки там, где уместно, или явно чистить коллекцию по TTL/событию. Демо-ручка показывает принцип: сначала убрать ссылку, потом GC сам сделает своё дело.

## Что мы сделали

Полный алгоритм из Part 0 на конкретном инциденте:

```
симптом (куча растёт и не возвращается после Full GC)
→ вопрос (утечка или легитимный рост live set?)
→ heap dump (jcmd GC.heap_dump) — два снимка во времени
→ MAT (Leak Suspects → Dominator Tree → Path to GC Root)
→ первопричина (static-коллекция LEAKED держит объекты)
→ fix + проверка (очистили ссылку → куча упала)
```

Сравнение трёх «растущих» симптомов серии:

| | Part 2 allocation churn | Part 3 humongous | Part 4 memory leak |
|---|---|---|---|
| Что растёт | темп аллокаций | Old Gen (во время инцидента) | куча (и после) |
| Куча | стабильна | колеблется | растёт |
| После Full GC (пока утечка активна) | возвращается | возвращается | **остаётся высокой** |
| Инструмент | async-profiler alloc / JFR | GC-логи / JFR | heap dump + MAT |

Оговорка: в демо `stop`/`fix` вызывают очистку `LEAKED`, поэтому после полного фикса куча вернётся к baseline. Отличие Part 4 в другом: **один Full GC без устранения удерживающей ссылки ничего не возвращает** — в отличие от Part 2/3, где достаточно остановить нагрузку.

Ключевой урок этой части: **не всякий рост кучи — утечка, и не всякая стабильность — здоровье**. Отличить утечку от легитимного роста можно только по поведению после Full GC и во времени — одним снимком кучи здесь не обойтись.
